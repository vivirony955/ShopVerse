# Plugin i18n

Plan §10 E16 — every user-visible string in a plugin component MUST
go through `t(key, defaultEn)`.

## Today: real locale-aware `t()`

`@shopverse/sdk-frontend` ships a locale-aware `t()` — it looks up the key in
the active locale's dictionary (`registerTranslations` / `setLocale`) and
returns the translation, falling back to the `defaultEn` string when there is
no entry, so English always works out of the box. A companion
`formatCurrency(amount, currency, locale)` handles money:

```ts
import { t } from '@shopverse/sdk-frontend';

<button>{t('plugin.priceAlerts.cta', 'Notify me on price drop')}</button>
```

Use stable keys (`<plugin>.<feature>.<role>`) so translation maps and
extraction tooling stay consistent.

Source: [packages/sdk-frontend/src/i18n.ts](../../packages/sdk-frontend/src/i18n.ts).

## Why not skip `t()` until i18n lands?

Adding `t()` later requires editing every plugin component. The
two-character cost today (`t('k', '...')` vs `'...'`) buys
zero-edit translatability when locale negotiation arrives.

## When locale negotiation lands (future wave)

The signature stays synchronous. The expected behaviour:

1. Plugin ships `locales/<lang>.json` next to its slot component:
   ```
   frontend/src/plugins/my-plugin/
     ├── Widget.tsx
     ├── index.ts
     └── locales/
         ├── en.json
         ├── hi.json
         └── ta.json
   ```
2. The locale is resolved at request-init from `Accept-Language` /
   user preference / URL prefix. The resolved locale lives in an
   RSC-friendly per-request store.
3. `t('plugin.priceAlerts.cta', 'Notify me on price drop')`:
   - Looks up `'plugin.priceAlerts.cta'` in the resolved locale's
     translation map.
   - Returns the translation if present, else `defaultEn`.

The plugin author writes the call once; the host-side i18n
infrastructure does the lookup.

## Key naming convention

`<plugin-id-tail>.<surface>.<role>`:

| Key | Surface | Role |
|---|---|---|
| `priceAlerts.cta` | PDP widget | call-to-action label |
| `priceAlerts.removed` | toast | success toast on deletion |
| `priceAlerts.set` | toast | success toast on set |
| `hello.cta` | tutorial widget | call-to-action |

Avoid plain strings as keys (`'Notify me'`) — they change with copy
edits and break the lookup. Use stable IDs.

## What the kernel handles

The kernel (and any kernel-owned component) does NOT use `t()` —
locale negotiation for kernel pages is the kernel's concern and
lives in a separate roadmap item. Plugin authors only ever interact
with `@shopverse/sdk-frontend`'s `t()`.

## What you MUST NOT do

- DON'T concatenate translated strings (`t('a', 'Hello') + ' ' + name`) —
  formatters need full sentences to handle word order.
- DON'T use `t()` for data values (numbers, dates) — those go through
  the kernel's `Intl`-backed formatters once they ship.
- DON'T fall back to `null` / `''` for `defaultEn` — it is the English
  source string AND the fallback when a locale lacks the key; empty
  defaults mean empty UI.
